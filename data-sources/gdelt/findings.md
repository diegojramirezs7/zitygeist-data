## Fetch recipe
<!-- endpoints, auth, rate limits, cadence, backfill depth -->
- **Two relevant endpoints, very different granularity.** GDELT 2.0's 15-minute export (`data.gdeltproject.org/gdeltv2/<timestamp>.export.CSV.zip`, pointer at `gdeltv2/lastupdate.txt`) is real-time but one file per 15 min — fine for a live snapshot, wasteful for a multi-month panel. GDELT 1.0's daily export (`data.gdeltproject.org/events/<YYYYMMDD>.export.CSV.zip`) is one file per *day* and already contains every country — this is the one that matters for the country-day panel.
- No auth, no observed rate limiting — it's a plain static file host, not an API. No shared throttle/retry module needed the way Wikimedia required.
- **`lastupdate.txt`'s pointer can be ahead of what's actually published** — hit a live ~30-minute gap where the pointer named a file that 404'd, and so did the interval before it. Not our bug; GDELT's own publishing pipeline has real gaps. Fixed by stepping back 15 minutes at a time until a file actually exists, rather than trusting the pointer blindly.
- Both schemas are fixed-width, no header row — column names have to be supplied positionally. GDELT 2.0's schema has 61 columns (includes `ADM2Code` per geo field), GDELT 1.0's has 58 (no `ADM2Code`) — genuinely different schemas, not a copy-paste bug. Verified both counts against real downloaded files before trusting either.

## Schema & quirks
<!-- native shape, junk patterns, gotchas found on real data -->
- **`CountryCode` fields are FIPS 10-4, not ISO 3166-1.** `UK` and `GM`, not `GB`/`DE` — used the ISO codes first and got ~0 rows for Germany and near-nothing for "GB" (a real but unrelated FIPS match) instead of an error, which made it an easy miss. CA/US/MX are identical in both standards, so this only bit newly-added countries. Worth remembering for every future country added.
- **Coverage is heavily wire-service/English-language skewed, not population-proportional.** Mean daily event count over a 90-day window (CA/US/MX/UK/GM): US ~29,700, UK ~5,380, CA ~2,600, GM ~825, MX ~490. Not proportional to population or news volume in any of those countries' own languages — matches the project's own brainstorm note that GDELT is wire-monitoring-driven, so non-English-source countries look artificially quiet.
- **`EventCode` is zero-padded ("010", "0211") and pandas silently strips the leading zero if read without `dtype=str`** — breaks any lookup against the CAMEO codebook (which is keyed on the zero-padded string) with no error, just wrong/empty matches. `fetch_gdelt_day` now takes an optional `dtype` param specifically for this.
- **GKG's `THEMES`/`PERSONS`/`ORGANIZATIONS` are article-level, not event-level** — a GKG row is one article, and its extracted fields cover everything mentioned anywhere in that article, with no positional link to any specific event within it. An article describing several events (real: one had 4) gives every one of those events the *same* full entity/theme list. GKG 2.1's `V2Themes`/`V2Persons` (15-min files, not touched yet) carry character offsets that could fix this properly; not pursued yet since GKG 1.0's daily file was enough to prove the concept.
- **Joining Events↔GKG via `CAMEOEVENTIDS` fans out for popular stories, not 1:1.** Same event ID shows up in *every* syndicated article's GKG row covering it (one wildfire event was referenced by 24 different outlets) — a plain explode-and-merge turned 91,182 events into 227,238 rows. Fix: pool themes across all covering articles into one set per event (`groupby(GlobalEventID)["THEMES"].apply(...)`) rather than joining article-by-article — gets back to exactly one row per event. Side effect: pooling across many articles is also why some events end up with 200+ largely-irrelevant themes (real example found) — worth revisiting (prefix-filtering out "entity mention" taxonomies like `TAX_FNCACT_*`, or picking one representative article instead of pooling) before this is trustworthy as a topic signal.
- Open question: are GKG theme tags usable as-is, or do we still need our own classification layer? Partially answered — not as-is; need noise filtering at minimum.

## Making an event human-readable
<!-- turning Actor1Code/Actor2Code/EventCode/GoldsteinScale into something legible -->
- **`Actor1Name`/`Actor2Name` are already event-scoped** — unlike GKG's article-wide `PERSONS`/`ORGANIZATIONS`, these are the actual actors CAMEO's extractor assigned to that specific event. Better source for "who" than GKG, and no join/fan-out risk.
- **Full CAMEO event-code hierarchy** (root → base → sub-code, ~310 codes) is a public GDELT lookup: `https://www.gdeltproject.org/data/lookups/CAMEO.eventcodes.txt`. We were only decoding the 20-bucket `EventRootCode`; the full table gives an actual verb (e.g. "Host a visit," "Use conventional military force") instead of just "Consult." Confirmed real and matching our data's `EventCode` format before using it — see `notebooks/gdelt/gdelt.ipynb`'s `decode_event_code` (falls back full code → base → root if a sub-code isn't in the table).
- Combining these two gives a decent one-line gloss (`Actor1Name + verb + Actor2Name`) straight from Events alone, no GKG needed — e.g. "RUSSIAN use conventional military force UKRAINE" (Goldstein -10.0). Still an algorithmic gloss, not a real summary; `SOURCEURL` is the escape hatch for that.
- **CAMEO glosses turned out too generic to be useful on their own** — real samples like "BANK make statement, not specified below SENATE" or "COMMUNITY consult, not specified below someone" don't convey what actually happened. Pivoted to a better source: **`slug_to_headline()`** parses the real headline straight out of `SOURCEURL`'s path (most news sites put it there), no article fetch needed. **88.3% coverage**, and dramatically more legible than the CAMEO gloss — e.g. "Sioux falls man charged with murder after domestic stabbing" vs. the equivalent CAMEO version. Cleaning needed real iteration against actual junk slugs: strip file extensions, strip trailing numeric/hex ID tokens (`b3026806`, `9.7291077`), strip a leading CMS-style numeric prefix (`26437230.murderer-...`), and return `None` (not a fragment) if fewer than 3 real words survive.
- **Design decision**: keep event-row granularity, don't dedupe/aggregate at the headline-building step. `NumMentions` is only meaningful per row, and an article that spawned several events (a real, confirmed pattern) legitimately produces several rows with that same headline. Any "top stories for city X" view is a query on top (group by place, sort by `NumMentions`, dedupe by URL if wanted) — not a decision to bake into the enrichment itself. Tested this end to end on Canadian cities (paired with the existing city-fingerprint grouping) and it produces a genuinely readable "what's this city's day about" digest — e.g. Ottawa's top story by mentions: "Ottawa awards Telesat $3B Arctic military satellite contract" (113 mentions).

## Granularity
<!-- confirmed spatial + temporal granularity on real data -->
- Daily is the practical floor for a multi-month panel (one request/day via GDELT 1.0). 15-minute granularity exists (GDELT 2.0) but at 96x the request volume for the same day — only worth it for near-real-time snapshots, not backfills.
- `ActionGeo_Type == 4` ("world city") is what lets you go finer than country — proven in the Canadian-city fingerprint (Toronto, Ottawa, Vancouver, etc. all separable within CA).

## Observation-spine mapping
<!-- which signal_types, which dims (place/entity/theme), cohort? -->
- First derived-observation experiment planned here: rolling per-country tone/volume baseline + deviation flags.
- **Done**: `notebooks/gdelt/gdelt.ipynb` builds a real country-day panel (CA/US/MX/UK/GM, 2026-05-06 to 2026-08-03, 450 country-days) with `events`/`goldstein`/`tone` per country-day, then a 14-day trailing rolling baseline (`shift(1)`, so a day's own value never leaks into its own baseline) with a z-score deviation flag on `tone`. 77/450 country-days flagged at `|z| > 1.5`. This is the "relative over raw" idea from the two-layer model, working on real data: **place** = country (FIPS code — needs a FIPS→ISO mapping to join against Wikimedia later), **temporal** = date, **signal_type** = `events`/`goldstein`/`tone` (raw) plus a derived `tone_z` (baseline deviation).
